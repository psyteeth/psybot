# Psybot — Telegram-бот «Психостоматология»

Бот для тест-драйва: разбирает вопросы по отношениям (схема A-B-C-D-E), помогает
с вопросом по зубам (шаблонный сценарий) и рассказывает о концепции
психостоматологии по данным Google-таблицы. Стек: Python 3.11+,
python-telegram-bot v21 (async, long polling), Claude API (`anthropic`), Google
Sheets (`gspread`), состояние — SQLite.

## Структура проекта

```
psybot/
  bot/
    main.py          — сборка Application, запуск long polling
    config.py         — переменные окружения, лимиты, константы
    db.py              — SQLite: пользователи, сессии, лимиты
    llm.py             — обёртка над Claude API (prompt caching)
    sheets.py          — логирование в Google Sheets + кэш таблицы концепции
    keyboards.py       — инлайн-клавиатуры
    handlers/
      menu.py          — /start, главное меню, текстовый фолбэк
      teeth.py          — ветка «Зубы»
      relationships.py  — ветка «Отношения» (A-B-C-D-E)
      concept.py         — ветка «Концепция»
  assets/teeth_chart.jpg — схема FDI
  deploy/                — systemd unit, deploy.sh, backup_db.sh
  data/                   — bot.db, bot_persistence.pickle (оба не в git) и бэкапы
  requirements.txt
  .env.example
```

## Персистентность разговоров (переживает рестарт/деплой)

`ApplicationBuilder().persistence(PicklePersistence(...))` в `bot/main.py` —
состояние каждого `ConversationHandler` (все три помечены `persistent=True`) и
`user_data` сохраняются в `data/bot_persistence.pickle`, автосохранение раз в
60 сек и при штатной остановке процесса (`systemctl restart` шлёт SIGTERM,
PTB перед выходом сбрасывает persistence).

Без этого КАЖДЫЙ деплой обнулял бы состояние разговора у ВСЕХ, кто в этот
момент был в середине разбора — не только у тестировщика, который его
вызвал (реальный баг, пойманный на проде: пользователь ответил на E-вопрос
ровно во время деплоя, бота «отбросило» в главное меню). `bot/debounce.py`
намеренно хранит буфер сообщений и хэндл отложенной джобы в собственных
модульных словарях, а не в `user_data` — job-объект JobQueue не picklable,
и класть его в персистентный `user_data` сломало бы сохранение целиком.

## Запуск локально

```bash
cd psybot
python3.11 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .env.example .env   # заполнить секреты
.venv/bin/python -m bot.main
```

Без `GOOGLE_SERVICE_ACCOUNT_JSON` бот работает, но логирование в Sheets и
таблица концепции отключены (сбой Google API не роняет бота — см. `bot/sheets.py`).
Без `ANTHROPIC_API_KEY` LLM-вызовы упадут исключением — нужен реальный ключ для
веток «Отношения»/«Концепция» и для разбора текстового номера зуба.

## Модели

- Ветки «Отношения» и «Концепция»: `claude-sonnet-5`.
- Меню/маршрутизация и ветка «Зубы»: `claude-haiku-4-5-20251001` (используется
  только для разбора текстового описания зуба и классификации приветствия —
  большая часть сценария «Зубы» вообще без LLM).
- Системные промпты кэшируются через `cache_control: ephemeral` (`bot/llm.py`).

## Доступ и лимиты (тарифы по членству в чатах, `bot/config.py::TIER_DEFAULTS`)

Бот доступен только тем, кто состоит в одном из двух Telegram-чатов (или
внесён вручную) — иначе показывает `NO_ACCESS_TEXT` вместо меню. Тариф
определяется автоматически через `getChatMember`, лимиты сбрасываются
**каждый календарный месяц**:

| Тариф | Как определяется | Отношения | Зубы | Концепция |
|---|---|---|---|---|
| `chat_unlimited` | участник приватного чата «исцеление отношений» (`RELATIONSHIPS_CHAT_ID`) | безлимит | безлимит | безлимит |
| `chat_member` | участник публичного чата психостоматологии (`PSYTEETH_CHAT_ID`, по умолчанию `@psy_teeth`) | 10/мес | 30/мес | 50/мес |
| `relative` | вручную в листе «Родственники» (`LOG_SPREADSHEET_ID`) — для членства через API не проверить | 10/мес | 10/мес | 30/мес |
| `none` | ни то, ни другое, ни третье | 0 | 0 | 0 |

Внутри одного разбора «Отношения» отдельно ограничены 40 сообщений
(`LIMIT_RELATIONSHIP_MESSAGES`) — после них бот мягко сворачивает к шагу E,
это не помесячный лимит.

Проверка членства кэшируется на 10 минут (`MEMBERSHIP_CACHE_SECONDS`,
`bot/membership.py`), чтобы не дёргать Telegram API на каждое сообщение.
Бот должен быть участником обоих чатов — иначе `getChatMember` всегда падает
и тариф уходит в `none`. Узнать numeric id приватного чата: добавить бота
туда участником и один раз выполнить `/chatid` в этом чате.

Счётчик разборов/сессий считает каждую **начатую в этом месяце** сессию
(включая брошенные на середине или прерванные из-за признаков насилия), а не
только доведённые до конца — иначе лимит можно обойти, просто не завершая
разбор.

### Где хранится счётчик и как посмотреть/поменять лимит вручную

Текущее «сколько использовано в этом месяце» — в SQLite (`data/bot.db`), это
не видно снаружи и руками не редактируется.

Персональный **лимит** переопределяется без правки кода, приоритет выше
тарифа по чату:

- Лист **«Лимиты (ручные)»** в таблице логов (`LOG_SPREADSHEET_ID`):
  колонки `user_id | ветка (Отношения/Зубы/Концепция) | лимит | комментарий`.
  `лимит` — число ИЛИ слово «безлимит». Вписал строку — бот подхватит её в
  течение 5 минут (`LIMIT_OVERRIDES_REFRESH_SECONDS`) и будет считать лимит
  этого пользователя по этой ветке равным указанному значению, независимо от
  тарифа по чату.
- Лист **«Родственники»** в той же таблице: колонки `user_id | комментарий`
  — присваивает тариф `relative` (10/10/30 в месяц) без ручного заполнения
  трёх строк в «Лимиты (ручные)».
- Команда **`/limits <user_id>`** в Telegram (доступна только тому, чей
  chat_id указан в `ADMIN_CHAT_ID`) — показывает тариф и по всем трём
  веткам: лимит, сколько использовано, сколько осталось. `user_id` берётся
  из колонки `user_id` любого листа таблицы логов.

Логика — в `bot/limits.py` (эффективный лимит) и `bot/membership.py`
(резолв тарифа по чатам).

## Тестовые данные и аналитика (`/stats`, ТЗ-доп. №2)

- `bot/config.py::TEST_USER_IDS` — user_id, которые считаются тестовыми
  (сейчас: 8001, 9001, 1234, 333, 444, 555, 0). Каждая строка во всех пяти
  лог-листах (Отношения/Зубы/Концепция/Лимиты/Выпады) автоматически получает
  колонку `тест` (да/нет) — это делает `SheetsLogger.append()` сам, по
  user_id в колонке B, без правки кода в каждой ветке (`bot/sheets.py`).
- `завершён` в «Отношения» считается ЦЕНТРАЛИЗОВАННО в
  `db.finish_relationship_session()` — да, только если реально заполнены A,
  B (подтверждённый), C, все D1–D8 и E; раньше это иногда передавалось
  хардкодом и могло разъехаться с реальным содержимым строки.
- Новые поля ветки «Отношения» (в конце листа, после старых колонок):
  `событие_до` (шаг A, если включён `ENABLE_PRIOR_EVENT_QUESTION` —
  по умолчанию выключен), `кто_другой` (авто-классификация Haiku по
  событию A, с уточняющим вопросом «А кто это для тебя?», если не
  определилось), `дискомфорт_до`/`дискомфорт_после`/`сдвиг` (шкала 0–10,
  до шага C и перед итоговыми E-вопросами; словесный ответ бот
  переспрашивает), `отражение_перед_E` (1–2 самых длинных дословных
  ответа из D1–D8, без пересказа — цитируются перед E).
- `/stats` (`bot/stats.py`) — сводка только по нетестовым строкам: разборы
  начато/завершено/%, распределение шага ухода, средний дискомфорт
  до/после/сдвиг и доля со сдвигом ≥2, распределение «кто другой», средняя
  длина ответов по D1–D8 (в словах), число упёршихся в лимит, число
  выпадов и категорий панчлайна. Только для `ADMIN_CHAT_ID`. Плюс
  автосводка раз в неделю (понедельник 10:00 по Бангкоку = 03:00 UTC,
  `bot/main.py::job_queue`).

## Правило «насилие/угрозы» убрано (ТЗ-доп. №4)

Ложное срабатывание: описание давления/агрессии другого человека («нападает,
приказывает, требует подчинения») — это обычный материал разбора A-B-C-D-E,
не повод останавливать сессию. `llm.detect_crisis`/`CRISIS_SYSTEM`
(проверка на насилие/угрозы) удалены полностью — их держала только ветка
«Отношения», в модуле «Скрытая потребность» не дублировались.

**Суицид/самоповреждение — отдельная проверка, приоритет как раньше, но
теперь в три уровня, не бинарно** (`llm.classify_self_harm` внутри
`hostility.precheck`, все ветки). Причина: в «Отношения» люди регулярно
говорят гиперболами о партнёре («жить не хочется», «убила бы себя от
злости») — раньше это тоже жёстко останавливало разбор, и бот становился
непригоден для реального использования.

- `"acute"` (прямое, конкретное намерение прямо сейчас/скоро) — уже НЕ
  мгновенный стоп. Бот сперва задаёт `SELF_HARM_CONFIRM_QUESTION`
  («на полном серьёзе, или это метафора?») и остаётся на том же шаге
  (`context.user_data["self_harm_awaiting_confirm"]`). Следующий ответ
  классифицируется `llm.classify_self_harm_confirm` на serious/not_serious/
  unclear: `not_serious` — исходный вопрос шага переспрашивается,
  разбор продолжается как ни в чём не бывало; `serious` ИЛИ `unclear`
  (осторожный дефолт — при сбое классификатора тоже) — уходит
  `SELF_HARM_TEXT` с телефоном горячей линии, `exit_step="crisis"`
  (раньше писалось как `self_harm_crisis`, переименовано для
  соответствия ТЗ-доп. №4). Вся логика — целиком внутри
  `hostility.precheck`/`_resolve_self_harm_confirm`, статус переиспользует
  существующие `"hostile"`/`"crisis"`, поэтому ни одна из трёх веток не
  менялась под эту цепочку.
- `"mild"` (суицидальная лексика-гипербола без признаков текущего
  намерения) — разбор НЕ останавливается, продолжается как обычно.
  Флаг копится в `context.user_data["self_harm_mild_flagged"]`, тихо
  уведомляется `ADMIN_CHAT_ID`, и в самом конце сессии (после основного
  финального сообщения — `_finish_e`/`cancel`/отказ/declined_D/
  hostility-closed во всех трёх ветках) отдельным сообщением уходит
  `hostility.SELF_HARM_SOFT_NOTE` — тёплая, не пугающая пометка с
  контактами помощи, ничего не блокируя по пути.
- `"none"` — ничего.

Разборы с `exit_step="crisis"` не списываются из месячного лимита
(`COUNT_CRISIS_TOWARD_LIMIT=False`, та же логика, что и `self_refused` из
доп. №3) — включая уже случившиеся ложные срабатывания задним числом,
раз это просто фильтр в запросе подсчёта, а не отдельный счётчик.

Новая колонка `примечание` (в конце, перед `тест`) — свободный текст для
ручных пометок вроде «ложное срабатывание, разбор возвращён».

**`/send <user_id> <текст>`** (`bot/handlers/menu.py::send_command`) — только
`ADMIN_CHAT_ID`, отправляет сообщение от имени бота указанному user_id,
логирует в новый лист «Админ-сообщения» (статус отправлено/ошибка — если
пользователь заблокировал бота, админ увидит ошибку в ответе). Текст берётся
из сырого текста сообщения (не `context.args`), чтобы не терять переносы
строк на многоабзацных сообщениях.

## Шкала катастроф с опорой и «избегание или интеграция» (ТЗ-доп. №5)

**D5 переписан целиком** — фиксированный текст с опорой 100 («полная жопа:
попал в катастрофу, лежишь в больнице, у тебя нет рук или ног...»), без
промежуточных точек, LLM его не переформулирует (риск смягчить). Своё
состояние: `D5_QUESTION`/`D5_HUNDRED_FOLLOWUP`, добавлены В КОНЕЦ enum
состояний (не вставлены посередине) — `persistent=True` хранит состояние
как целое число на диске, перенумеровка сломала бы уже начатые разборы.
Ответ принимается только числом 0-100 (`_parse_scale_100`), текст ответа —
в `d5_comment`. Если 100 — один уточняющий вопрос, ответ принимается без
спора; если человек сам называет новое число — записывается в
`d5_catastrophe_scale`, исходные 100 — в `d5_original`
(`llm.extract_revised_scale`).

**«Избегание или интеграция»** (`llm.classify_exit_intent`, порог
`EXIT_INTENT_CONFIDENCE_THRESHOLD=0.7`) — проверяется на каждом ответе C/
C_feeling/D1-D8 (кроме D5, там число)/E/E_correction/E_followup, но только
ДО первого срабатывания (дальше не тратим вызовы, шаг запоминается один
раз). Срабатывание НЕ прерывает разбор — только после того, как `_finish_e`
уже отправил обычное финальное сообщение, добавляется ещё один обмен:
уточняющий вопрос (`llm.extract_disowned_behavior` подбирает короткую фразу
поведения другого человека из A/B), затем по ответу
(`llm.classify_avoidance_integration`) — абзац про избегание, про
интеграцию, или оба (если неясно), плюс ссылки. Запись строки в
«Отношения» намеренно ОТКЛАДЫВАЕТСЯ до разрешения этого обмена — иначе
пришлось бы патчить уже отправленную строку в Sheets. Новое состояние
`EXIT_INTENT_CLARIFY`.

**3.1 Лист «Диалоги»** — одна строка на каждую реплику (и бота, и
человека) в «Отношения»: `timestamp | user_id | username | ветка |
номер_разбора | шаг | кто | текст`. Раз PTB `Message`/`CallbackQuery`
используют `__slots__`, перехватить `reply_text` на конкретном объекте
сообщения нельзя (протестировано, `AttributeError`) — вместо этого весь
файл переведён на общий хелпер `_send(update, context, session_id, step,
text, **kwargs)`, который шлёт и логирует одним вызовом.

**3.2 Запрет ложных заявлений об улучшении** — `llm.generate_session_summary`
получил `discomfort_before`/`discomfort_after`; если после не меньше до,
в промпт добавляется жёсткий запрет на фразы вроде «тебе уже легче».

**3.3** — `OTHER_PERSON_SYSTEM` получил рабочий контекст (зарплата,
увольнение, директор, руководитель, дедлайн → `начальник`).

## Дожим конкретного ответа + полный лог переписки (ТЗ-доп. №6)

### Часть 2 — «дожим» на шагах A и B (заменяет ТЗ-доп. №3 целиком)

Разбор строится вокруг КОНКРЕТНОГО поведения другого человека (шаг A) и
конкретного долженствования к нему (шаг B) — общих слов («боится
коммуникации», «проблема во мне») недостаточно. Новый классификатор
`llm.classify_concrete_answer(step, text)` (Haiku, строгий JSON:
`target: other|self|unclear`, `concrete_behavior: bool`) вызывается из
`bot/handlers/relationships.py::_check_dozhim` вместо старого
`_check_self_target`. Ответ принят только если `target=other` И
`concrete_behavior=true`.

- **Отдельные счётчики попыток на A и на B** (`context.user_data`,
  `rel_dozhim_a_attempts`/`rel_dozhim_b_attempts`) — если A прошёл с 1-й
  попытки, B всё равно получает свою полную лестницу из 3 попыток.
- Попытка 1 — уточняющий текст с просьбой продолжить фразу («Меня в нём
  бесит то, что он…» / «Он должен был бы…», `DOZHIM_ATTEMPT1_TEXT`).
- Попытка 2 — жёстче (`DOZHIM_ATTEMPT2_TEXT`, фирменный резкий тон автора).
- Попытка 3 — закрывает сессию: если финальный ответ `unclear` (юлит) —
  `DOZHIM_EVASIVE_CLOSE_TEXT`; если `self` — `DOZHIM_SELF_CLOSE_TEXT`
  (переиспользует `SELF_REFUSAL_TEXT` из доп. №3 + строка с @psyteeth).
  После закрытия — кнопки «В меню»/«Зубы» (`menu_and_teeth_keyboard()`).
  Такой разбор **не** списывается из месячного лимита (та же логика, что
  и раньше: `self_refused=1` исключается в
  `db.count_relationship_sessions_this_month`).
- Новые колонки в «Отношения» (в конце, перед `тест`): `session_id`,
  `попытки_A`, `попытки_B`, `исход_проверки` (`принят с первого раза` /
  `переформулировал` / `отказ_юлит` / `отказ_самообвинение`). `шаг_выхода`
  для закрытых дожимом сессий — буквально `отказ_юлит`/`отказ_самообвинение`.
  `/stats` показывает распределение исходов и сколько шагов A/B потребовали
  доп. попыток.
- Протестировано на реальных вызовах Claude по всем примерам из ТЗ (10/10):
  «боится коммуникации искренней», «мне всё равно, что он делает, я хочу не
  бояться боли», «проблема во мне», «я сама всё разрушаю» — все верно
  отклонены; конкретные примеры «он постоянно перебивает…», «он должен был
  бы предупредить заранее…» — верно приняты.

### Часть 1 — полный лог переписки

**Лист «Диалоги»** (`bot/sheets.py::DIALOGUES_HEADER`) расширен и теперь
пишется из **всех трёх** веток (раньше — только «Отношения», доп. №5, п.3.1):
`timestamp | user_id | session_id | username | ветка | номер_разбора | шаг |
кто | текст | тип | тест`.

- `session_id` — не отдельная колонка в БД, считается на лету:
  `f"{user_id}_{started_at}"` (`_dialogue_session_id()` в каждом из трёх
  handler-файлов). Та же строка добавлена колонкой в «Отношения» и «Зубы»,
  чтобы листы можно было склеить по `session_id`. У «Концепция» нет сессий
  в БД (только счётчик сообщений) — там `session_id` живёт один цикл
  вопрос→(уточнения)→ответ в `context.user_data`, а `номер_разбора` пустой.
- `тип`: `обычный` по умолчанию, `уточнение` (дожим/переспрос), `отказ`
  (закрытие дожимом/острые симптомы зубов/офтоп), `кнопка` (нажатие
  инлайн-кнопки, текст = `callback_query.data`). Значения `кризис`/
  `панчлайн`/`лимит` из ТЗ **не задействованы** — см. «Известные
  ограничения» ниже.
- `bot/handlers/teeth.py` и `bot/handlers/concept.py` получили те же
  `_send`/`_log_turn` хелперы, что и `relationships.py` из доп. №5 (единый
  вызов = отправка + запись строки; `Message`/`CallbackQuery` из PTB на
  `__slots__`, перехватить `reply_text` точечно нельзя — уже упирались в
  это в доп. №5).

**Лист «Диалоги (матрица)»** (`bot/dialogue_matrix.py`) — сводная таблица:
один столбец на разбор, одна строка на фиксированный шаг (`username`, `дата`,
`A — бот/человек`, `проверка на себя A — бот/человек`, `B`, `B сверка`, `C`,
`ответ «я бы…» — бот`, `D1`…`D8` (бот/человек), `отражение перед E — бот`,
`проверка на себя B — бот/человек`, `E`, `избегание/интеграция`,
`финал — бот`, `прочее`). Строится **из** листа «Диалоги» по `session_id` в
момент закрытия разбора (`_log_session()`/`_log_and_build_matrix()`) —
единый источник правды, как и написано в ТЗ. Реплики, не попавшие ни под
один фиксированный шаг (например, ответ на D_confirm «да, хочу дальше»),
уходят в `прочее`; несколько реплик на одном шаге склеиваются переносом
строки с префиксом `бот:`/`человек:`. Первый столбец заморожен
(`ws.freeze(cols=1)`), включён перенос текста. Для «Зубы» — отдельный лист
`Диалоги (матрица) Зубы` с пятью строками из ТЗ (`номер зуба`, `самое
страшное`, `как себя чувствует`, `финальный ответ`, `острые симптомы`) —
там строки НЕ разбиты на бот/человек (одна ячейка на тему, обе реплики
через перенос строки). У «Концепция» матрицы нет (нет фиксированных шагов,
только линейный лог) — соответствует ТЗ.

Проверено на реальной боевой Google-таблице: прогнан полный тестовый цикл
«Зубы» (все шаги + матрица + очистка), прогнана сборка матрицы «Отношения»
на синтетических строках «Диалоги», тестовые строки/столбцы после проверки
удалены из живой таблицы.

**`/dialog <session_id или username>`** (`bot/handlers/menu.py::dialog_command`,
только `ADMIN_CHAT_ID`) — читает лист «Диалоги», если аргумент совпадает с
существующим `session_id` — берёт его, иначе ищет последнюю (по timestamp)
сессию с таким `username` (без `@`, без учёта регистра). Шлёт текст простым
списком `[шаг] кто: текст`, режется на сообщения по 3500 символов.

**Бэкфилл прошлых сессий (с 2026-09-25) — НЕВОЗМОЖЕН, честно.** Проверено
через `journalctl --user -u psybot --since 2026-09-25` на сервере: в логах
только старты процесса, трейсбеки ошибок и ретраи Anthropic SDK — нигде не
логируется текст отправленных/полученных сообщений (в коде до этой сессии
не было ни одного `logger.info(текст_сообщения)`). Восстановить прошлые
диалоги неоткуда — придумывать их не стал, как и просили. Лист «Диалоги»
начинает наполняться только с этого деплоя.

### Известные ограничения этой реализации

Не всё из фразы ТЗ «логировать вообще всё, включая служебные сообщения
(приветствие, меню, лимиты, отказы, панчлайны)» попало в лист «Диалоги» —
сознательно урезано ради вменяемого объёма изменений за один заход:

- **Панчлайны модуля «Скрытая потребность»** (`bot/hostility.py`) — не
  дублируются в «Диалоги». У них уже есть свой подробный лист «Выпады»
  (цель, категория, текст панчлайна, реакция) — просто не связан
  `session_id`.
- **Приветствие/меню** (`bot/handlers/menu.py`) и **уведомления о лимите**
  (`limit_exhausted_text`, во всех трёх ветках) — тоже не дублируются в
  «Диалоги» (лимит по-прежнему пишется в отдельный лист «Лимиты»). Типы
  `тип=кризис`/`тип=лимит`/`тип=панчлайн` из ТЗ поэтому нигде не
  проставляются.

Если это важно — можно дописать отдельным заходом: технически несложно
(у `hostility.precheck`/`menu.show_menu` уже есть branch/session контекст),
просто не влезло в этот объём правок.

## Живые баги из первых реальных разборов, часть 2 (сессия AlisaHaay)

Тот же живой разбор дал ещё два независимых бага — оба уже пофикшены и задеплоены:

- **`_strip_code_fence` падал на пояснении после JSON.** Haiku на
  `classify_concrete_answer` для шага A вернула ПРАВИЛЬНЫЙ вердикт
  (`target=self` — Алиса описывала СВОЁ поведение: дразнит тренера, флиртует
  с её мужем, ей нравится, когда та ревнует — ни слова про то, что БЕСИТ в
  поведении другого), но следом дописала `**Обоснование:** ...` после JSON,
  хотя промпт требует строго JSON без пояснений. `json.loads` падал на
  `Extra data`, классификатор проваливался в safe-default
  (`target=other, concrete_behavior=true`) — который ИНВЕРТИРОВАЛ верный
  вердикт модели и пропустил Алису на шаг B, хотя она должна была попасть в
  лестницу дожима уже на A. `_strip_code_fence` переписан: теперь ищет
  первую сбалансированную JSON-структуру (`{...}`/`[...]`) в тексте ответа,
  игнорируя всё до и после — чинит эту же уязвимость во всех 11 местах,
  где используется тот же паттерн `json.loads(_strip_code_fence(raw))`, не
  только в classify_concrete_answer.
- **Планка `concrete_behavior` на шаге B была строже, чем нужно.** Реальный
  ответ «Он должен был бы защищать, оберегать, учить и т.п.» отклонялся как
  «неконкретный» (названы глаголы-действия, просто обобщённые, не про
  единственный случай) — сессия закрывалась жёстким «юлишь» текстом на
  живом, старающемся ответить человеке. По прямому указанию автора
  `CONCRETE_ANSWER_SYSTEM` ослаблен: `concrete_behavior=true`, если названо
  ХОТЬ КАКОЕ-ТО действие/глагол, пусть даже списком обобщённых обязанностей
  — false только когда действий вообще не названо (голая оценка/эмоция).
  При этом критерий `target` для self/other ужесточён отдельно (иначе
  ослабление concrete_behavior задело и его — при первой попытке фикса
  текст Алисы про СЕБЯ ошибочно переклассифицировался в target=other):
  теперь явно указано, что рассказ про СВОИ действия — self, даже если
  попутно упомянута реакция другого человека на них.

Все 12 регрессионных кейсов (10 из спеки доп. №6 + оба живых случая) прошли
на реальных вызовах Claude, дважды подряд для проверки стабильности.

## Живые баги из первых реальных разборов (после ТЗ-доп. №6)

Найдены по логам в «Диалоги (матрица)» на реальных сессиях, не из ТЗ:

- **D5 гендерно окрашен**: «ты попал в катастрофу» не годится для женщины.
  Убрано слово «попал» (прошедшее время) — «ты в катастрофе, лежишь в
  больнице...» (настоящее время, род не проявляется).
- **E-вопрос заранее утверждал, что мысль «теряет свою силу»** — человек мог
  прямо ответить, что стало ХУЖЕ, а бот продолжал вести себя так, будто
  сработало. `E_QUESTION_SYSTEM` переписан на честный, не предполагающий
  результат вопрос («что-то изменилось, или всё так же?»). Новый
  классификатор `llm.classify_e_shift` — если ответ явно «не изменилось/
  хуже», сессия закрывается честным текстом (`E_NO_INSIGHT_TEXT`,
  приглашение на диагностику) вместо того, чтобы выискивать несуществующий
  инсайт через `ask_e_followup`.
- **«Диалоги (матрица)»: ячейка «прочее» без указания шага** — несколько
  разных шагов, не попавших в фиксированные строки, сваливались в одну
  ячейку без пометки, откуда что. Теперь в «прочее» (и только там) каждая
  реплика помечена `[шаг]`.
- **«Зубы»: диагностика за другого человека** — ничего не мешало матери
  пройти диагностику «за дочь», а бот вёл себя как обычно. Новый
  классификатор `llm.classify_diagnosis_subject` на шаге «самое страшное»:
  если ответ явно про другого человека — несовершеннолетнего направляем
  через расстановку (без объяснения, что это такое, с приглашением на
  диагностику при необходимости), взрослого — спрашиваем прямо, почему он
  сам не проходит диагностику, и если мотивация тревожная/виноватая —
  добавляем наблюдение специалистов психостоматологии про сепарацию. Не
  блокирует разбор — мягкая вставка, разбор продолжается как обычно.
- **«Зубы»: ответ на «Каким ты тогда себя чувствуешь?» — ярлык, а не эмоция**
  («не целый», «не справившийся» вместо настоящего прожитого чувства).
  Критерий уточнён автором: засчитывается только НЕГАТИВНОЕ САМООПРЕДЕЛЕНИЕ,
  по сути отвечающее на «что со мной не так?» в одной из трёх категорий —
  умственная/социальная/физическая (боту это в промпт зашито, клиенту вслух
  не озвучивается). `llm.classify_feeling_depth` (`is_deep`/`category`/
  `label`) — если ответ не дотягивает, бот цитирует его и докапывается
  («какой ты сам(а), если одним словом? Закончи: «Я...»»), с оговоркой, что
  диагностика — штука не самая комфортная, но самый важный шаг к пониманию
  причины проблемы с зубами. До 2 дожимов (`FEELING_DIG_MAX_ATTEMPTS`),
  дальше принимает ответ как есть — не блокирует разбор бесконечно.

## Открытые вопросы (см. ТЗ, помечено «уточнить у заказчика»)

- Тарифные лимиты (10/10/30, 10/30/50) — константы в `bot/config.py::TIER_DEFAULTS`,
  легко поменять.
- Точная формулировка сообщения при признаках насилия/угрозы в «Отношениях»
  (сейчас — `CRISIS_TEXT` в `bot/handlers/relationships.py`).
- Условие «позиции не сошлись» в споре по концепции: реализовано как два
  подряд определённых LLM спорных сообщения (`DISPUTE_STREAK_THRESHOLD` в
  `bot/handlers/concept.py`) — после этого бот предлагает написать
  @psyteeth и (если задан `ADMIN_CHAT_ID`) уведомляет админа.

Модуль «Скрытая потребность + SET-панчлайн» (`bot/hostility.py`, дополнение к
ТЗ) — свои открытые пункты:

- Контакты помощи при суицидальном кризисе: сейчас `@psyteeth` + линия
  8-800-2000-122 (реальная бесплатная круглосуточная линия РФ), см.
  `SELF_HARM_TEXT` в `bot/hostility.py` — заказчик может захотеть другие/
  дополнительные контакты.
- «Дверь назад» в разбор: реализовано как «редко, на усмотрение модели» —
  промпт прямо просит не добавлять её в большинстве ответов (эталонные
  примеры из ТЗ сами её не используют). Если нужно «всегда» или «никогда» —
  правится в `PUNCHLINE_SYSTEM` в `bot/llm.py`.
- Мат: бот зеркалит, только если пользователь уже матерился в этой сессии
  (простая regex-проверка `PROFANITY_RE`, не LLM) — реализовано как в ТЗ.
- Включать ли модуль на шаге D «Отношений»: сделано «нет» (по умолчанию из
  ТЗ) — сопротивление на D считается материалом разбора, не выпадом; кризис
  (суицидальный) при этом всё равно проверяется всегда. Переключается через
  `skip_hostility=True` в вызове `hostility.precheck(...)` внутри
  `d_question` в `bot/handlers/relationships.py`.

## Что проверено локально (симуляция без реального Telegram/Claude)

- Полный проход «Отношений» A → E со всеми восемью оспариваниями, запись
  всех колонок в SQLite (число_сообщений считается верно).
- Признаки насилия на шаге A обрывают разбор, ведут к специалисту, лог
  помечен `exit_step=crisis`.
- Тарифный лимит (10 разборов/мес для `chat_member`) блокирует 11-ю попытку
  с нужным текстом; пользователь не в чатах и не в списке «Родственники» не
  видит меню вовсе.
- «Зубы»: номер словами → подтверждение через инлайн-кнопки; невалидный
  номер вне схемы FDI отклоняется с просьбой попробовать снова; острые
  симптомы (сильная боль/отёк/температура/кровотечение) обрывают сценарий
  на любом шаге.
- «Концепция»: ответ с релевантным листом таблицы, эскалация при споре,
  строки в Sheets формируются с верными колонками.
- Сбой Google Sheets (нет `GOOGLE_SERVICE_ACCOUNT_JSON`) не роняет бота —
  запись просто логируется как потерянная.

Не проверено (нужен реальный прогон с настоящими токенами): фактическое
качество ответов Claude, реальная запись в Google Sheets, поведение
long polling под Telegram.

## Деплой на VDS (Ubuntu 22.04, Weecere, Fremont CA)

**Реально развёрнуто и работает** на 69.40.207.79. Ниже — как именно, включая

решили без root, где возможно).

### 1. Безопасность сервера (сделано)

- Root-пароль остался прежним (сессия, в которой его меняли, не смогла
  выполнить смену — см. заметку ниже); root по SSH и вход по паролю
  **отключены** (`PermitRootLogin no`, `PasswordAuthentication no` в

- Пользователь `psybot` — вход только по SSH-ключу (пара сгенерирована в
  `psybot/.deploy_secrets/psybot_admin_key`, **не коммитить**), с ограниченным
  `NOPASSWD`-sudo только на `systemctl {start,stop,restart,status} psybot` и
  `journalctl -u psybot`.
- `ufw` включён, разрешён только OpenSSH.
- ⚠️ Root-пароль всё ещё тот, что был изначально (менять пока не удалось из-за
  ограничений sudo в сессии деплоя) — валиден для веб-консоли хостера. Сменить

### 2. Python 3.11 — без root, через `uv`

Пакетный менеджер apt требовал root, которого не стали расширять сверх
необходимого. Вместо `apt install python3.11`:

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh   # ставится в ~/.local/bin, без sudo
uv python install 3.11                             # готовый бинарник, без компиляции
```

### 3. Код — приватный GitHub-репозиторий + деплой-ключ

Репозиторий: `git@github.com:psyteeth/psybot.git` (приватный). На сервере —
свой read-only deploy key (`~/.ssh/psybot_deploy_key` у пользователя `psybot`,
добавлен в Settings → Deploy keys репозитория без права записи), настроен
через `git config core.sshCommand` в `/home/psybot/psybot/.git/config`. Код в
`/home/psybot/psybot/` (не `/opt/psybot` — `/opt` root-only, `psybot`
пользователем без root не пишет туда).


### 4. Секреты

`.env` на сервере — не в git (в `.gitignore`), скопирован туда напрямую
(`scp`), права `600`, владелец `psybot`.

### 5. Автозапуск — user-level systemd, не системный

`/etc/systemd/system/` тоже root-only. Вместо системного сервиса — юнит
пользователя `psybot`:

```bash
# уже сделано:
mkdir -p ~/.config/systemd/user
cp deploy/psybot.service ~/.config/systemd/user/psybot.service
systemctl --user daemon-reload
systemctl --user enable --now psybot
loginctl enable-linger psybot   # чтобы сервис жил без активной SSH-сессии — сработало без root
```

Важно: юнит **не использует** `EnvironmentFile=` — сложный JSON-ключ сервис-аккаунта
с кавычками и `\n` внутри ломается парсером systemd (`MalformedError: No key
could be detected`). Секреты грузятся самим ботом через `python-dotenv`
(`bot/config.py`), это уже работает и без `EnvironmentFile`.

Управление:
```bash
export XDG_RUNTIME_DIR=/run/user/$(id -u)   # нужно при заходе не через полноценный логин-шелл
systemctl --user status psybot
journalctl --user -u psybot -f
```

(`git pull` на сервере через deploy key, `pip install -r requirements.txt`,
`systemctl --user restart psybot`. Запускать после `git push` изменений в `main`.)

### 8. Память

1 ГБ RAM, из которых на сервере уже занято другим процессом (`vibe-trading`,
не связан с psybot — тот же VDS используется для нескольких ботов). Psybot
сам по себе — около 50 МБ в простое. Таблица концепции кэшируется в памяти
процесса (обновление раз в час, `bot/sheets.py::ConceptStore`), не грузится
целиком в каждый запрос к LLM. Своп уже настроен (2 ГБ) — на сервере он был
ещё до этого деплоя.
